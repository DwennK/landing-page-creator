# Evidence-Based Creative Repair Loop

Use when the rendered hero or page fails `review-checklist.md`. A working build is the start of visual review, not its conclusion. Continue autonomously within the authorized scope.

## Diagnose Before Changing

1. Capture and inspect the failed surface at the relevant desktop/mobile viewport and scroll state. Keep this baseline for comparison.
2. Name the visible defect precisely: “the product occupies too little of the hero to read” is actionable; “needs more wow” is not.
3. Identify the cause: weak concept, inadequate asset, poor composition, generic content structure, missing signature choreography, or implementation defect.
4. Choose the smallest substantive change that addresses that cause. Preserve successful work, business behavior, and unrelated user edits.

## Match the Repair to the Failure

| Failure | Substantive repair |
| --- | --- |
| Transferable concept | Return to concept selection and choose a different visual idea rooted in the actual offer, object, or proof. Change its composition/story, not only the palette. |
| Weak or defective asset | Fix the asset brief, crop, lighting, geometry, or layer plan; edit/regenerate only what is needed, or use a stronger real asset. Inspect it before rebuilding around it. |
| Anonymous hero | Recompose the focal object, type relationship, scale, and negative space around the chosen idea. Keep the offer and CTA immediately readable. |
| Generic lower sections | Replace filler with concrete evidence, a useful comparison, a specific objection, or a meaningful interaction. Delete content that serves no purpose. |
| Motion without a signature | Storyboard a real transformation with readable initial/intermediate/resolved states and a purposeful handoff. Repeated entrance effects cannot substitute for the requested scene. |
| Weak mobile translation | Redesign crop, hierarchy, timing, or the scene itself for touch and the smaller viewport; a deliberate static resolution is valid. |
| Functional or accessibility defect | Fix the broken behavior directly; do not launch a redesign to avoid debugging it. |

Do not add gradients, shadows, particles, icons, fake metrics, extra cards, or longer scroll distances as a substitute for a causal repair. Do not generate assets endlessly without a changed brief and diagnosed defect. Respect user limits on time, tool use, and paid resources.

## Repair, Compare, Decide

For each creative cycle:

1. Save a recoverable baseline of task-owned changes without resetting or overwriting other work.
2. Implement the grouped changes that address the highest-impact failed gates.
3. Run the app again; inspect matching before/after viewport and scene states. For motion, also exercise real scrolling and interactions.
4. State which observed defect disappeared and check for regressions in clarity, mobile, CTA, focus, reduced motion, and performance as relevant.
5. Accept an improvement only when the evidence supports it. If it remains generic, change the underlying idea on the next cycle instead of repeating cosmetic tweaks.

Use up to **three substantial creative repair cycles after the initial implementation, shared across hero and full-page review**. Stop early when all applicable gates pass. Routine corrections within a cycle are not new creative cycles. Functional fixes and checks required for the changed behavior still need completion; the creative budget does not waive them.

After the budget, or if a real tool/content blocker prevents further progress, preserve the strongest working version. Report the specific failed or unverified gate, what was attempted, and the next useful remedy. Do not claim the result is spectacular, accepted, or complete. Ask for input only when the remedy truly depends on missing user information or authorization. Never conceal a failed gate by lowering the brief, inventing evidence, or scoring yourself higher.
